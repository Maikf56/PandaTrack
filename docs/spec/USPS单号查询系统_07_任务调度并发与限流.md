# USPS 单号查询系统 07：任务调度、并发与限流

## 1. 模块目标

通过持久队列、有限 Worker、租约、租户公平调度、浏览器环境隔离和 Provider 限流，控制系统资源与上游请求风险。系统吞吐目标必须由 Linux 云服务器实测和 Provider 明确限制共同决定；服务器能承载的并发不等于 USPS 允许的速率。

## 2. 功能范围

- Scheduler、Dispatcher、Redis broker、FetchJob 状态和数据库租约。
- Worker 池、浏览器 profile/环境池、会话和代理绑定、single-flight。
- 多环境×多标签页并发执行：环境数按服务器资源推算、每环境多标签页、代间换指纹出口、人类间隔。
- 跨客户待查单号汇总去重（同时提交去重 + 库内近期查询去重）与失败多轮回炉。
- 全局、租户、profile/环境和 Provider 维度的并发/速率控制。
- 基于延迟、错误率、挑战/拒绝信号的自适应限流、熔断和恢复。
- 队列公平性、重试预算、死信、容量测试和观测指标。

不包含：页面解析规则（02）、业务计费判定（06）、客户可见进度组件（04）。

## 3. 关键设计

### 3.1 持久队列和 Worker

PostgreSQL FetchJob 是任务事实源，Redis 只承载可恢复队列。Scheduler 依据新提交、客户主动刷新、缓存新鲜度和终态规则生成任务；同一 tracking/reason 通过 single-flight 避免重复抓取。Worker 领取前取得数据库 lease，lease 过期后可回收；处理顺序为领取任务→检查 Provider/熔断→执行→事实与 outbox 事务提交→ack。任务状态包含 pending、claimed、waiting_for_session、opening_page、collecting_response、parsing、validating、writing、succeeded、retry_scheduled、dead_letter 等。

租户公平使用按租户轮转/权重队列；急件有独立但受预算约束的优先级。任务不足时不启动空闲浏览器，队列过载时排队并告警，不无限创建进程。

### 3.2 独立浏览器环境

“一个环境”指一套自洽的 ClawBrowser 指纹（内核/UA/OS/语言/时区/地理位置/WebGL，见 02 第 3.1 节）+ 一个 Socks5 轮换出口 + 一个独立 profile（user_data_dir、Cookie/LocalStorage、会话状态）+ 固定浏览器版本与可追踪健康状态。ClawBrowser 档案根据出口 IP 自动匹配指纹（时区/语言/地理位置）。采集主网络为 udealproxy 住宅代理：每个 profile 在启动时绑定一个代理出口（启动时自动分配 IP），并在会话有效期内复用；用户名携带多区域轮换（覆盖代理服务的所有可用区域），每批随机选州。不跨环境复制 Cookie/挑战材料。

#### 3.2.1 环境重建失败兜底

一个环境从创建到可用要依次经过：档案创建（绑定指纹与轮换出口）→ 浏览器进程启动 → CDP 端点就绪 → 出口准入检查（见 02 第 3.1 节）。任一环节失败都不能让队列任务丢失或被误判为业务失败。方案按失败发生的位置分层兜底：

| 失败位置 | 典型原因 | 兜底动作 | 任务归属 |
|---|---|---|---|
| 启动前预检不通过 | 可用磁盘低于单实例门槛、内存不足、Provider 凭据失效、内核缺失 | 不启动环境，记录脱敏原因并告警；不消耗任务重试次数 | 任务留在队列，等资源恢复 |
| 档案创建/启动失败 | clawctl 启动异常、CDP 端口未就绪、API key 失效 | 换档案名与轮换出口有限次重建（默认 3 次）；仍失败则本环境本轮退出 | 任务退回队列，由其他环境接管 |
| 出口准入失败 | 出口连通性/延迟/USPS 首页检查不合格 | 在发查询前换候选出口重试（见 02 第 3.1 节三层准入），不携带业务请求 | 不扣费、不计业务失败 |
| 会话中途崩溃 | OOM、浏览器进程被杀、会话目录写满 | lease 超时回收后在 3.3.2 的可回炉轮次中换环境换出口重查 | 归 RETRYABLE（browser_crash） |
| 连续大面积启动失败 | 磁盘/内存耗尽、Provider 侧故障 | 触发保护性暂停调度并告警，停止继续创建环境，防止紧循环放大故障 | 队列保留，人工排除基础设施故障后恢复 |

关键约束：

1. **基础设施失败与业务失败分离**：磁盘/内存/凭据/内核等启动类失败记为环境级故障，不落入单号的 `error_class`、不触发 Provider 熔断、不冲正积分；只有真正发出查询后收到的上游拒绝/挑战才按 02 第 5.8 节处置。
2. **重建有界**：单次环境重建次数、单轮全局重建次数都设上限（默认各 3 次），避免坏环境下无限重试；超限转为保护性暂停并告警。
3. **清理必达**：无论启动成功或失败，`finally` 中都删除本批会话目录并按 3.3.1 的双根清扫超期孤儿目录，防止重建过程反复写满磁盘（磁盘写满会直接导致下一次 clawctl 启动失败）。
4. **可观测**：记录环境级启动成功率、重建次数、预检拒绝原因分布和会话目录占用，作为容量标定和故障定位的依据（见 3.5）。

**并发模型**：环境是并发单位，标签页是环境内的工作单位。每个环境（代）顺序处理最多 `tabs_per_environment`（默认 10）个标签页，同一时刻一个标签页一次查询；多个环境由线程池并发（`max_workers = max_environments`，由 `auto_max_environments()` 按内存推算，`USPS_MAX_ENVIRONMENTS` 显式设置时优先）。因此"每环境同时只跑一个活动查询"与"多标签页"不矛盾：单环境内标签页顺序执行，环境之间并行。遇到限制不能自动换 profile 或批量换出口继续请求。

### 3.3 容量估算

系统侧的理论处理能力可用 `throughput ≈ C × B / T` 估算，其中 C 是并发 Worker/profile 数，B 是每批有效单号数，T 是批次平均完成时间。该公式只估算系统处理能力，不表示上游允许的速率。有效 C 由以下最小值决定：CPU/内存/文件句柄/连接资源可承载量、稳定 Worker/profile 数、Provider 经验证的并发/速率限制、全局运维配置上限。

开始标定时先配置保守单 Worker 和单 profile，不预设安全 QPS。批次上限按 Provider 实际支持确定，不能超过 35 条已知单次上限；若不能验证页面批量处理的结果与错误隔离，就逐单号执行。每环境速率和间隔通过逐级测试记录，不把某次成功外推为通用阈值。

#### 3.3.1 并发环境数自动推算

并发环境数 `max_environments` 由代码按服务器可用内存自动推算，不再手动硬编码。用户 2026-11-17 就提出"按服务器配置自动确定环境数"，2026-11-18 落地实现。

**推算公式**（`usps_dispatcher.py` 的 `auto_max_environments()`）：

```python
max(2, (可用内存MB - 900M底座) // 550M单实例)
```

- 底座 900M ≈ Python worker + PostgreSQL + Redis + 操作系统余量（实测 2G 机器）
- 单实例 550M ≈ 一个 Chromium 会话的实测峰值（含波动余量，实测 RSS 396-485MB）；除数统一为 550，与 00 §5、02 §3.3 及本节配置表一致（原推算公式处的 500 为笔误，见 11 号文档 D1 裁定）
- 无硬编码上限，服务器配置越好并发越多；02 表格旧残留「≤5」已删除

**环境变量优先级**：
- `USPS_MAX_ENVIRONMENTS` 未设置 → 自动推算（推荐）
- 显式设置 → 用显式值（运维临时调整时用）

**按统一公式的推算结果**（4G 的旧值「6」按式算不出，为文档笔误，见 11 号文档 D1）：
- 2G 内存机器（可用 1.1G）→ 自动得 2
- 4G 内存机器（可用 3.2G）→ 自动得 4（**原「6」为笔误**）
- 8G 内存机器（可用 7.8G）→ 自动得 12（无上限）

> 注：以上为按公式的推算值，真实容量须在目标 Linux 验收区用 1/2/5/10 环境逐级标定后形成基线，不把推算当实测（00 §12、08）。

**内存不足的后果**（2026-11-18 实测）：
- 2G 机器开 3+ 并发 → 内存耗尽、系统换页、OOM killer 强杀浏览器进程、SSH 失联
- 2G 机器开 5 并发（默认值）→ 必然复现上述问题
- 修复后 2G 机器强制并发=1，内存从 115M 可用恢复到 1.1G

**会话目录磁盘泄漏**：
- ClawBrowser 每批查询在 `~/.cache/clawbrowser/sessions/<档案名>` 写约 500M 会话数据
- `profiles rm` 不清理该目录，一天泄漏数 GB
- 修复：`_cleanup_session_dir()` 在 finally 里删本批目录 + `_sweep_stale_sessions()` 清超期孤儿目录（默认 30 分钟，`USPS_CLAW_SESSION_MAX_AGE_H` 可调）
- 双根清理：同时覆盖 `USPS_CLAW_CACHE_DIR` 和 `$HOME/.cache` 两个位置

#### 3.3.2 跨客户汇总去重与多标签页分批

对应 `usps_dispatcher.py` 的 `BatchDispatcher.dispatch()`，多客户同时提交时不逐客户各自查询，而是先汇总再统一编排：

```text
多个客户的待查单号（来自 B 库请求表 / FetchJob）
  → ① consolidate：保序去重，同一时刻重复单号只留一份（记录出现次数用于审计）
  → ② recent_checker(numbers, 24h)：排除库内近期已成功抓取的单号
       去重服务异常 → 退化为不去重，不阻断主流程
       被跳过单号 → 直接沿用库中事实，客户关系/投影照常建立
  → ③ chunk(numbers, 35)：切成 N 个页面请求批次（一个批次 = 一个标签页一次查询）
  → ④ assign_slots：每 10 个标签页为一代（generation），栈内 tab_index 0..9
       → 线程池按 max_environments 并发消费批次
       → 每处理 tab_interval_requests（默认 10）个标签页插入随机化人类间隔
  → ⑤ 汇总结果；可重试失败进入下一轮，换环境换出口（max_rounds 默认 3）
       命中 fail-closed 错误 → 停止该单号，按 02 第 5.8 节自动换 IP → 换环境 → 回炉重查
```

**关键配置（`DispatchConfig`，均可在验收区标定）**：

| 参数 | 默认 | 含义 |
|---|---|---|
| `max_environments` | 自动推算：`max(2, (可用内存MB - 900) // 550)`，`USPS_MAX_ENVIRONMENTS` 显式设置时优先 | 并发环境数，线程池大小 |
| `batch_size` | 35 | 一个标签页一次查询的单号数，不超 USPS 单次 35 上限 |
| `tabs_per_environment` | 10 | 一代环境内处理的标签页数，之后换指纹+出口 |
| `tab_interval_requests` | 10 | 每多少标签页插一次人类间隔 |
| `tab_interval_ms` | 2500 | 间隔基数，随机 0.6~1.4 倍 |
| `max_rounds` | 3 | 失败回炉最大轮次 |
| `recent_window_hours` | 24 | "库里最近查过"判定窗口 |

**"5 环境 × 10 标签页"例子的准确拆解**：1 万条单号去重后按 35 切片约 286 个页面批次，每 10 个批次为一代（约 29 代），代间换指纹与轮换出口，由 5 个并发环境轮流消费；每 ~10 个标签页插一次随机间隔。用户口述的"分 5 批每批 2000 条"是按环境数预切大块的等价说法，实现采用"按 35 细切片再分给环境"，因为细片更利于失败隔离、断点续写和租户公平。100 万是受理总量，排队逐批处理，不是并发数。

**可回炉 vs 立即停止**（分类以 02 §5.1 失败矩阵为唯一权威，见 11 号文档 D3）：

- `RETRYABLE`（换出口/换环境回炉）：`challenge`（换州级出口，超 `max_attempts=3` 转 TERMINAL）、`network_timeout`、`browser_crash`、`upstream_5xx`、`probe_*`、`proxy_gateway_unreachable`、`soft_throttled`、`parse_failed`（同一任务一次受控重取）。
- `TERMINAL`（fail-closed，不回炉）：`rejected`、`quota`、`source_invalid`、`page_type_unknown`、`quality_gate_rejected`、`rate_limited`；命中即终态失败，该批积分按 06 冲正。
- `circuit_open`：熔断冷却半开探路，**不计入连续失败阈值**；未超限走 `retry_scheduled`，超限 `dead_letter`。
- 未知错误保守归为可重试一次，绝不归为成功。`page_type_unknown` 为 TERMINAL（须先修分类器），旧清单将其列为 RETRYABLE 已按本节纠正。

### 3.4 自适应控制状态机

所有阈值均为初始观测策略，不是 USPS 安全保证；每个 Provider 必须在实际验收中重新标定。

| 状态 | 触发条件（初始参考） | 动作 |
|---|---|---|
| 绿 | 真实结果解析成功；P95 相对基线稳定；无拒绝/挑战；错误率稳定 | 保持当前值；每个完整观察窗口最多增加 1 个 Worker 或约 10% 并发，观察后再决定 |
| 黄 | P95 连续 2 个窗口较基线上升约 50%；普通超时/解析失败上升；成功率下降约 5 个百分点 | 并发乘 0.7–0.8；请求间隔乘 1.5–2；暂停增加并观察至少 2 个窗口 |
| 红 | HTTP 403/429、Access Denied、挑战/CAPTCHA、额度耗尽、明确拒绝或非目标页面被识别为成功 | 立即暂停受影响 Provider/会话新请求，打开熔断，保存脱敏证据并按 02 第 5.8 节自动换 IP → 换环境 → 回炉重查；不自动批量换出口、换指纹、加压或重试 |
| 冷却恢复 | 熔断冷却期后自动半开放行一次探路 | 成功则复位、失败继续熔断；连续失败达 `max_attempts` 则终态失败；全程自动，无人工介入 |

**熔断器死锁修复（2026-11-18 定案）**：

原实现熔断后只能人工复位，而熔断期间不可能成功，形成永久死锁。修复方案：

1. **冷却期自动半开**：熔断后进入冷却期（默认 10 分钟，`USPS_CIRCUIT_COOLDOWN_MIN` 可调），冷却期满自动放行一次探路请求
2. **连续失败阈值**：连续失败 N 次自动打开熔断（默认 30，`USPS_CIRCUIT_FAILURE_THRESHOLD` 可调），打开后按冷却期自动半开
3. **challenge 移出 stop 名单**：州级轮换下每次重试都是全新出口 IP（实测通过率约 2/5），challenge 应换出口回炉而不是直接打死，仍受 `max_attempts=3` 上限约束
4. **circuit_open 不计入连续失败**：熔断拒绝本身属自反馈错误，排除在阈值判定外，防止历史高计数让阈值永真
5. **半开放行时清零计数**：防止累积的历史失败计数让阈值判定永远满足

**实测验证**：
- 修复前：10 分钟内死信从 168 暴涨到 824（熔断拒绝 + 自反馈死循环）
- 修复后：死信稳定在 188、熔断保持关闭、challenge 自动回炉、真实成功持续流入

普通瞬态网络错误可按有限次数指数退避；收到挑战/拒绝不适用自动重试。熔断状态和解除理由写入审计日志。

### 3.5 监控指标

- Provider：真实数据命中率、状态/事件解析成功率、P50/P95/P99、超时率、5xx、403、429、挑战、额度耗尽、拒绝和页面类型分类。
- 分组维度：Provider 配置版本、Worker、环境（generation）、标签页（tab_index）、会话、出口、时段和租户；记录脱敏标识，不记录秘密。
- 调度质量：跨客户汇总去重命中数、库内近期去重跳过数、每轮批次/标签页数、人类间隔实际值、各轮回炉数量、环境代轮换次数。
- 系统：活动 Worker/profile 数、浏览器启动成功率/崩溃数、CPU、内存、文件句柄、网络连接数、队列深度、最老任务年龄、任务重试与死信。
- 数据链路：A 库写入延迟、AOutbox 积压、B 投影延迟、SSE 延迟、Redis 重建次数。
- 资源成本：udealproxy 流量/余额、代理流量消耗、单结果字节数、数据库/磁盘增长和备份结果。

### 3.6 分阶段验证

在已购 Linux 云服务器验收区执行。固定测试号码集合、浏览器版本、会话配置、出口、每轮时间窗和数据记录格式；只用获准测试样本。按单 profile 基线→1 环境→2→5→10 环境逐档验证，每档先固定低速率，再逐步提高一个变量。记录启动时间、批次大小、每环境请求间隔、耗时、P50/P95/P99、真实命中、解析错误、HTTP/页面分类、CPU/内存、队列年龄和出口/会话标识。

每档在多个时段重复观察；任何红档信号立即停止，不继续升档。只有连续多轮真实结果正确、错误分类稳定且无限制信号时，才形成“已观察容量范围”；仍不得宣称不会被封禁。10 标签页×35 成功的既有样本只进入证据记录，不直接作为默认容量。

### 3.7 四分支判定、刷新预算与批次交错

后端保鲜和「检查更新」必须先做四分支判定，不能简化成“库里有数据就跳过”：

1. 事实不存在或已失效 → 创建 FetchJob 抓取。
2. 事实存在但已终态 → 沿用事实，不重复抓上游。
3. 事实新鲜且未到 `next_sync_at` → 沿用事实，0 上游请求。
4. 上游暂停、熔断或额度受限 → 保留任务与客户关系，延后重试或按 02 第 5.8 节自动换 IP → 换环境 → 回炉重查。

**跳过抓取不等于跳过客户关系**：不论是否发起上游请求，提交产生的 customer_tracking、reservation 和投影都必须正常建立。客户提交后按 `(operation_id, batch_seq)` 分片交错进入租户公平队列；1,000,000 条提交按并发环境数均衡分批，环境数由内存自动推算。禁止整批连续占用 Worker；SSE 只按批次聚合进度。真正发往 USPS 的批次由 3.3.2 的汇总去重 + 35 切片 + 环境代分配决定，与明细分片是两层。

异步首结果 P50 ≤15 s / P95 ≤60 s 为目标观察值，必须在目标 Linux 验收区按真实 Provider 数据标定，不作为固定承诺。后台非终态刷新受活跃单号 7 天窗口和全局每日刷新次数上限控制。udealproxy（Socks5）是采集主网络，按 profile 绑定轮换出口；ClawBrowser 启动后自动检测出口可用性（见 02 第 3.1 节代理出口可用性检测），不合格在发查询前换候选出口；代理异常不静默直连，查询中命中阻断后不自动批量换出口，按 02 第 5.8 节处置。
