### C2 single-flight 索引（已确认修正）

### D1/D2 并发公式与上限
- **事实**：
  - 00 §5.1 表：`max(2,(可用内存MB-900)//550)`；00 §5 正文写 2G→2、4G→6、8G→12。
  - 02 §3.3：`max(2,(可用内存MB-900)//550)`；表格却写「并发环境数 ≤5」。
  - 07 §3.3.1 推算公式：`//500`，并写 4G(可用3.2G)→6、8G(可用7.8G)→12；07 §3.7 配置表又写 `//550`。
- **算术核对**：`//550`：2G(可用≈1.5G→按本机可用口径) 不确定；4G 可用 3.2G→`(3200-900)//550=4`；8G 可用 7.8G→`(7800-900)//550=12`。`//500`：4G→`(3200-900)//500=4`；8G→`(7800-900)//500=13`。**两者都算不出「4G→6」**（要得 6 需除数≈380）。
- **裁定**：统一用 `max(2, (可用内存MB - 900) // 550)`，`USPS_MAX_ENVIRONMENTS` 显式设置优先。按此公式 8G→12 与多数文档一致；**4G→6 判为文档笔误，按 4G→4 落地**。并发**无硬上限**（删除 02 表格「≤5」的旧残留）；§02「首发从最低值起」保留为分阶段启动策略，非上限。

### D3 失败分类（权威口径）
- **冲突**：02 §5.1 失败矩阵：`challenge` 可回炉；07 §3.4「challenge 移出 stop 名单」。但 07 §3.3.2 又把 `challenge` 列入 TERMINAL；`page_type_unknown`、`circuit_open` 在 02/07 归类相反。
- **裁定**：以 **02 §5.1 失败矩阵为唯一权威**（原文称其为「实现、告警、验收的直接依据」）：
  - `challenge` = RETRYABLE：换州级出口回炉，超 `max_attempts=3` 转 TERMINAL。
  - `page_type_unknown` / `quality_gate_rejected` = TERMINAL：fail-closed，先修分类器。
  - `circuit_open` = 冷却半开探路，**不计入连续失败阈值**，未超限走 `retry_scheduled`。
  - 07 §3.3.2 的清单按此对齐修订。

### F1 采集会话前置：USPS 首页暖场（2026-11-19 实测定案）
- **事实**：跳过首页直接打开 `tools.usps.com/go/TrackConfirmAction?tLabels=...`，页面为空标题 + 约 252KB 混淆脚本、`_abck` 固定含 `~-1~`、正文长度 0，等待 60 秒不放行；换州级出口、重建会话均无效。先开 `https://www.usps.com/` 停留约 8 秒建立会话，再开跟踪页，立即得到真实轨迹（正文≈4800、`.tb-step=1`、单号正确绑定）。
- **裁定**：把"打开 USPS 首页暖场"从可选的连通性探针升级为**每个采集会话的强制前置步骤**，写入 02 §3.1；换出口/换环境重建会话后必须重新暖场。此硬拦归类为探针失败 / `page_type_unknown`，不按可等待的 `challenge` 处理。
- **误判教训**：曾把"空标题+大混淆脚本"直接套用 §5.1 的 `challenge` 分类器并原地轮询等待，浪费时间；分类器样本不等于可绕过信号，须结合是否暖场判断。

### F2 网络/流量口径（2026-11-19 实测澄清）
- **事实**：当前采集 profile 为 `--manual-proxy socks5 → 127.0.0.1:1080 → udealproxy 住宅出口`。对 USPS 连续访问 3 次，`clawctl proxy-traffic` 的 `used` 始终 `1.00 MiB` 不变，证明采集流量不经 ClawBrowser 官方账户。`proxy_traffic: exhausted / remaining 0 B` 仅是账户余额状态；`clawctl verify` 的 `proxy expected=US actual=N/A` 检验的是官方托管代理区域，manual 模式天然不适用。
- **裁定**：明确三种网络/流量职责（服务器本地中继 / udealproxy 三方出口 / ClawBrowser 官方账户流量），写入 02 §3.1 新表；禁止把前两者的失败归因于账户流量耗尽。geo 预检由本地中继截胡 `ipinfo.io`/`ipapi.co` 并以同出口真实 geo 应答，保证指纹/geo/出口一致。
- **影响**：后续排查 USPS 拦截按 5.8 顺序（暖场 → 换出口 → 回炉），不再检查账户流量这一无关项。

### G1 单号处理五步细则（2026-11-19 客户口径定案）
- **事实**：客户提出从"提交单号"到"结果送达前端"的五步链路：① 判定 USPS 并清洗（非 USPS 自动清理）→ ② 跨客户同时间窗汇总去重 → ③ 库匹配（存在且终态直接调取；存在且非终态、查询时间 ≤20 分钟直接调取；反之再查询；不存在则查询）→ ④ 按总数量分批次并发查询 → ⑤ 结果入库并同步输送前端。原方案 ①②④⑤ 已有实现（06 §3.2、07 §3.3.2），但 ③ 只有笼统的 `recent_checker 24h`（"24h 内成功抓过就跳过"），无终态/新鲜度分层，与客户口径不一致。
- **裁定**：
  1. 五步链路固化为 **07 §3.8**（调度侧权威），各步实现归属：①=06 Cleaner v1，②③④=07，⑤=07+05/04。
  2. **库匹配判定取代 `recent_checker 24h`**：按"不存在→查询 / 终态→直接调取 / 非终态且最近一次查询尝试 ≤`fresh_window_minutes`（默认 20 分钟）→直接调取 / 非终态且超窗→再查询"四序判定；判定依据用 A 库既有字段（`fetch_attempt_log`、终态枚举），无 schema 变更；配置项 `recent_window_hours=24` 同步改为 `fresh_window_minutes=20`。
  3. "同步输送前端"与 00 §5 静默保鲜的边界：**本次操作主动查询的新结果按批次聚合 SSE 实时推送**；后台保鲜的历史更新仍客户触发式呈现。00 §5 前端更新行已加例外说明。
  4. 计费免扣（06，30×24h，按客户）与库匹配（07 §3.8，按全库单号）仍是两层，06 §3.6 口径已同步。
- **影响**：07 §3.3.2 第②步、§3.7 四分支、配置表、交付清单，06 §3.6，00 §2.3/§5 均已回写。

### G2 竞品交互优化方案吸收（2026-11-19 评审定案）
- **事实**：`开发文档/02_辅助资料/FrogTracking交互设计分析与优化方案.md` 与 `FrogTracking优化原型.html` 已评审。其"规则即交互"优化项（实时解析面板、成本预估条、提交确认弹窗、变化感知、重查默认勾选异常态、可见性感知轮询、新手引导、设计系统）与既有"客户侧不设独立预览步骤/确认步骤、静默保鲜"口径存在表面冲突。
- **裁定**：
  1. **新增提交前预估接口** `POST /api/v1/submissions/estimate`（09 §5.2.1）：服务端按 06 同规则清洗与资格判定，幂等、不入账、不写 reservation、不产生 operation，**不构成报价**、不设报价有效期；提交仍一步完成。前端实时解析面板与成本预估条只展示该接口结果（防抖 ≥300ms），禁止前端本地计费；预估条常驻"预估，以提交结果为准"。06 §3.3、09 §3.1/§4/§5.2.1、04 §1 原则 2 已回写。
  2. **大批量防呆确认 ≠ 报价确认**：仅当 >1,000 条或选择非默认组时弹确认卡（目标组/条数/预估积分），确认后提交；不产生报价、不计费、不入账。不视为违反"无预览/无报价确认"原则。
  3. **变化感知**：状态跃迁卡片 1.2s 强调色描边淡出 + "N 个状态更新"摘要条 + 筛选栏更新徽章；与"不自动改行"的边界：只对本次订阅操作的新结果高亮，不弹通知。
  4. **检查更新默认勾选异常态**（未找到/异常/投递失败/退回/暂未获取），勾选面板实时显示"终态 X 条将自动沿用"；破坏性操作确认弹窗内嵌"先导出备份"入口。
  5. **可见性感知轮询 + 连接状态指示器**（实时/轮询/离线三态）补入 04 §8.2；与既有 SSE/Last-Event-ID 机制叠加而非替代。
  6. **新手引导**（04 §5.13）：首次登录 3 步引导（示例单号带"示例"标记，不伪造数据）、双状态常驻图例、空状态即引导。
  7. **设计系统**（04 §4.4）：中性灰阶 + 单强调色 `#0F766E`、数据列等宽字体、8pt 间距/行高 44/紧凑 36、两级阴影、120–200ms 微交互；语义色仍只用于物流状态。
  8. 不吸收项：竞品"价格计算器/免登录试查/API 开通进度"属其营销与商业化策略，超出本系统范围，本版不引入。
- **影响**：04 新增 §4.4/§5.13，§5.4/§5.6/§8.2/§12 增补；06 §3.3；09 新增 §5.2.1；验收用例新增 17–21。

### H1 前端独立主目录与分服务器部署形态（2026-11-19 定案）
- **事实**：用户目标是"前后端绝对隔离，前端只通过 API 获取数据"。经澄清：前端获取数据本来就只有 `/api/v1/*` + SSE 一条通道（从不直接读库），A/B 双库是后端内部数据归属划分，不是前端访问方式。真正欠缺的是两点：① 前端代码仍混在后端 `apps/` 目录里，物理上不独立；② "前端与 API 分服务器部署"无部署形态约定。
- **裁定**：
  1. **前端独立主目录**：`apps/web` 迁出为顶层 `frontend/client`（客户前端）；管理端后续落地为 `frontend/admin`。`frontend/` 不含任何 Python/数据库代码，构建产物为纯静态文件；CI 路径同步（working-directory 与 cache-dependency-path）。
  2. **部署形态双轨**（01 §3.2.1）：形态 A 当前默认同机同域（Cookie 同域最稳）；形态 B 可选分服务器/CDN + API 独立域名，触发条件为安全审计要求分机、前端需 CDN/独立扩容、或前后端需独立发布节奏。切换不改业务代码，只动 dist 位置 + DNS/Nginx/CORS 配置；形态 B 必须落实 CORS 白名单（禁止 `*`）、`SameSite=None; Secure` 会话复核、SSE 跨域头白名单、API base URL 环境变量注入。
  3. **概念口径固话**：前后端隔离的边界是 HTTPS API（前端只见 `/api/v1/*`）；A/B 分库管的是"采集敏感数据永不进客户可见的库"。两者不再混用表述。
  4. 隔离证据链：前端黑名单扫描（构建产物无内部地址/库表/secret）+ 数据库仅回环/私网监听 + BFF 进程独持连接串。
- **验证**：`frontend/client` 迁移后 vitest 17/17 通过、vue-tsc+vite 构建通过（gzip 42KB）；全仓 `apps/web`/`apps/client-web`/`apps/admin-web` 引用清零。
- **影响**：10 号文档目录树/§3.4/§4/§5 重写；docs/PROJECT-STRUCTURE.md 同步；01 新增 §3.2.1；04 头注增补；`.github/workflows/ci.yml` web job 路径更新。
