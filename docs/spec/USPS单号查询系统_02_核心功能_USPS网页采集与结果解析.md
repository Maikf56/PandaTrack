# USPS 单号查询系统 02：核心功能、USPS 网页采集与结果解析

> 状态：当前唯一施工规格。本文是模块 02 的细化设计，与 00 总方案及 01、05、06、07、08、09 模块共同执行；决策日志只记录沿革，不替代本文。
>
> 目标：采集执行后端已落地为 ClawBrowser 指纹浏览器，批量并发调度已落地为多环境×多标签页调度器（含跨客户汇总去重、按 35 切片、每代换指纹/出口、人类间隔、失败多轮回炉）。真实 USPS Linux Provider 的稳定吞吐、批量结果隔离、解析器、脱敏证据、告警和防逆向部署仍属于本模块的实现/验收项。

## 1. 模块目标

在已购 Linux 云服务器上，以受控、可审计、可恢复的方式访问 USPS 官方查询页面，取得真实物流状态和事件，解析为系统标准事实，并通过 A 库 outbox 向客户投影链路提供数据。

本模块的核心规则：

1. 客户生产结果必须来自真实 Provider。
2. 真实 `usps_web` Provider 默认 `enabled=false`。启用前必须完成实施评审、目标 Linux 运行验收、停止条件验证和容量标定。
3. 遇到 HTTP 403、429、Access Denied、验证码/挑战页、额度提示、明确拒绝或页面无法确认时，按分级自动流程处理：换出口 IP → 换环境 → 回炉重查；达到重试上限或熔断半开仍失败才终态失败，全程无人工介入。轮换出口是采集主网络的基本能力，阻断后第一顺位即换 IP。不复制 Cookie、不隐藏浏览器特征、不提高并发、不打码或等待挑战通过；
4. 数据写入坚持“宁可不写错，不可猜一个结果”：页面类型不明、字段缺失、单号不匹配、状态冲突、时间倒置时，按失败或质量拒绝处理，不写成成功轨迹。
5. 系统吞吐和上游访问额度必须分开。单次 35 条只是输入批量事实，不是 QPS、安全并发额度，也不能推导“环境越多吞吐线性增长”。
6. 采集执行后端固定为 ClawBrowser 指纹浏览器。一个环境 = 一套自洽指纹 + 一个 Socks5 轮换出口 + 一个独立 profile。
7. 查询前先做出口可用性检测（连代理网关 + 访问 USPS 首页/连通性探测，见 3.1 节），不合格的出口在发查询请求前换掉；这与“查询中命中阻断后停止并报告”（见 5.8）是两个不同环节，不得混为一谈。

## 3. 执行链路与状态口径

### 3.1 单次任务链路

```text
FetchJob 领取/租约
  → 检查 Provider enabled / emergency_stop / circuit_open
  → 按环境槽生成 ClawBrowser 档案（一套指纹 + 一个 Socks5 轮换出口）
  → 出口可用性检测：TCP 探测代理网关 → 暖场站点 → USPS 首页探测
      （连不通/首页异常/空 body 判为不可用，换下一个候选出口，尚未发查询请求）
  → 打开查询页并提交 1~35 个规范化单号（批量能力待验收）
  → 页面类型校验
  → 逐单号提取状态、事件、时间、地点、原始文本
  → 八道质量闸门
  → A 库单事务写 Tracking / TrackingEvent / parse_evidence / sync_outbox / FetchJob 状态 / provider_health
  → 确认队列消息
  → sync-agent 单向摆渡到 B 库投影
  → finally：关闭浏览器、删除档案、清理约 500M/批的会话目录
```

采集只通过真实浏览器内页面自身响应/DOM 取得结果；不伪造页面请求参数、不直调内部 XHR、不以 curl_cffi 或裸 HTTP 替代页面查询。采集执行后端为 ClawBrowser 引擎级指纹浏览器：指纹在 C++ 引擎层注入（历史记录 2026-11-18 实测 3/3 通过真实结果页，为当时验证记载、非当前代码事实），裸内核 Playwright/Patchright 直连查询页实测被 Akamai 拦截，故不作为兜底。多环境采集默认采用 udealproxy 住宅代理：Socks5 协议、一个 profile 绑定一个代理出口，出口在浏览器启动时自动分配并在会话有效期内复用。独立环境、持久化会话和代理绑定用于正常并行接入；阻断后按 §5.8 自动换出口 IP → 换环境 → 回炉。

#### 采集会话前置：USPS 首页暖场（2026-11-19 实测定案）

**强约束**：每个浏览器会话在打开跟踪页之前，必须先打开 `https://www.usps.com/` 首页并停留约 8 秒，让页面脚本建立 Akamai 初始会话 cookie，再导航到跟踪页。跳过此步直接打开 `tools.usps.com/go/TrackConfirmAction?tLabels=...` 会被稳定硬拦：页面为空标题 + 约 252KB 混淆脚本、`_abck` 固定含 `~-1~`、`document.body.innerText` 长度为 0，等待 60 秒也不会放行；这不是可等待执行的 JS 挑战（与 §5.1 `challenge` 的"空标题+大混淆脚本"分类器特征需区分：本例是未暖场导致的硬拦，归类为 `page_type_unknown` / 探针失败，不应等待）。

- 实测证据（2026-11-19，profile + udealproxy 住宅出口）：先开首页 → `body.innerText.length≈7100`（正常首页）；再开跟踪页 → `length≈4800`、`.tb-step=1`、`.product_summary=1`、单号正确绑定、摘要为真实文案。同一出口同一会话跳过暖场则 `length=0`、持续 `~-1~`。
- 因此 §3.1 链路中"暖场站点 → USPS 首页探测"不是可选的连通性探针，而是**采集会话的强制前置步骤**：既做出口准入判断，又建立后续跟踪页所需的会话状态。实现上放在每个环境档案创建后、任何查询提交前；换出口/换环境重建会话后必须重新暖场。
- 入口 URL 会由 `tools.usps.com/go/TrackConfirmAction?tLabels=<no>` 跳转到 `tools.usps.com/tracking/<no>`，这是正常跳转，不是拦截；以 `.tb-step` 是否出现判定是否取得真实结果，不以 URL 形态判定。

#### 网络与流量口径（2026-11-19 实测澄清，防再次误判）

采集链路涉及三种不同的"网络/流量"，职责边界必须分清，禁止混为一谈：

| 项 | 归属 | 在本系统中的角色 | 是否消耗 ClawBrowser 账户流量 |
|---|---|---|---|
| 服务器本地网络 / 本地 SOCKS5 中继（127.0.0.1:1080） | 自建 | 浏览器连接入口；转发流量、截胡 geo 预检（见下） | 否 |
| udealproxy 住宅代理（三方） | 用户提供 | **真正的出口 IP**，USPS 看到的来源；profile 以 `--manual-proxy socks5` 绑定 | 否 |
| ClawBrowser 账户流量（`proxy_traffic`，1 MiB 试用额度） | ClawBrowser 官方 | 仅当用官方 `--country US` 出口/官方 verify 时才消耗；manual 三方代理模式不走它 | 仅官方出口模式消耗 |

- **事实**：当前采集为 manual 三方代理模式，出口是 udealproxy 住宅 IP。实测对 USPS 跟踪页连续访问 3 次，`clawctl proxy-traffic` 的 `used` 始终为 `1.00 MiB` 不变，证明采集流量**不经** ClawBrowser 官方账户。`proxy_traffic: exhausted / remaining 0 B` 只是账户余额状态显示，不代表当前链路在扣费，更不是采集失败的原因。
- **禁止的误判**：不得把 `proxy_traffic exhausted` 或 `clawctl verify` 中 `proxy ... actual=N/A`（该项检验的是 ClawBrowser 官方托管代理区域，manual 三方代理模式下天然不适用）当作 Akamai 拦截的根因。历史上曾据此误判并浪费排查时间。USPS 拦截的根因排查顺序见 5.8 与本节"首页暖场"。
- **geo 预检**：ClawBrowser 会访问 `ipinfo.io` / `ipapi.co` 判断出口地理位置，对住宅 IP 常返回 406/429。本地 SOCKS5 中继截胡这两个域名的请求，用经同一粘 IP 出口查到的真实 geo 应答，保证"指纹区域 / geo 预检 / 实际出口"三者一致（对齐本文"环境与指纹构成"约束）。

#### ClawBrowser 环境与指纹构成（2026-11-19 定案）

一个"环境"是一套自洽的浏览器指纹加一个绑定的代理出口。指纹由 ClawBrowser 档案在引擎层成套注入，系统负责"选区域模板 + 绑定出口 + 保证两者一致"，不自研逐字段伪造。档案需覆盖的指纹维度至少包括：

| 维度 | 内容 | 一致性要求 |
|---|---|---|
| 浏览器内核 | 多个受支持版本的 Chromium 内核，按档案模板选取 | 与 UA 版本声明一致 |
| User Agent | 与所选内核/操作系统匹配的真实 UA | 不得出现内核与 UA 版本矛盾 |
| 操作系统 | 档案模板声明的 OS（与 UA 一致） | 与 UA、时区、语言共同自洽 |
| 语言 | `en-US` 及浏览器语言头 | 固定 en-US |
| 时区 | 任何时区 | 必须与出口 IP 所在地一致 |
| 地理位置 | 与出口对应的地理信息 | 与出口 IP 区域一致 |
| WebGL Info | 厂商（vendor）与渲染器（renderer） | 使用真实显卡/引擎指纹 |

关键约束：**地理位置、时区指纹必须与代理出口 IP 区域一致**。

#### 代理出口可用性检测（2026-11-19 定案）

查询请求发出之前，先判断这个出口"能不能用"，避免把带查询的单号浪费在坏出口上。准入按三层递进，任一层失败即判该出口不可用：

| 层级 | 检查 | 失败分类 | 动作 |
|---|---|---|---|
| 1 网关可达 | TCP 连接 udealproxy 的 host:port（约 5 秒超时） | `proxy_gateway_unreachable` | 换下一个候选出口；不启动浏览器，不碰 USPS |
| 2 连通性/延迟 | 暖场站点（如 `api.ipify.org`）取出口 IP 与往返延迟 | `network_timeout` | 判定出口质量，超时或高频失败则换出口 |
| 3 USPS 首页 | 打开 USPS 首页并停留，检查 HTTP 状态与非空 body | `probe_bad_status` / `probe_empty_body` | 换出口；首页异常时不进入查询页 |

"不行就换"的准确含义：**在查询请求发出前的准入阶段**，从候选出口池换一个尚未被证明不可用的出口。此阶段未提交任何单号查询，属于正常的上岗前检查，不是绕过风控。轮换范围覆盖代理服务的所有可用区域（见州级 IP 池小节），并记录每次尝试的脱敏出口引用。

准入检查与"阻断后处置"的边界（必须严格区分，见 5.8）：
- 准入阶段换出口 = 出口本身连不通/延迟过高/首页异常，尚未发查询请求，允许自动换下一个候选出口。
- 查询阶段出 403/429/挑战/额度/明确拒绝 = 已经发出查询并被上游拒绝，按 5.8 自动换 IP → 换环境 → 回炉重查；达到重试上限或熔断半开仍失败才终态失败。
- `challenge` 例外：按 11-18 熔断修复定案，挑战可换州级出口自动回炉（最多 3 次），这是"查询未取得结果时的重试"，与"拿到明确拒绝后换 IP 绕过"不同；仍受 `max_attempts` 约束。

#### 州级 IP 池随机轮换（2026-11-18 定案）

udealproxy 提供 13 个美国州级区域（alabama/colorado/california/florida/illinois/louisiana/michigan/mississippi/newyork/ohio/texas/virginia/newjersey）+ 1 个泛美（us）共 14 个 IP 池。**实测州级池信誉差异显著**：同一时刻德州/俄亥俄通过率约 2/5，加州/纽约/佛州 0/12+。系统在每次创建浏览器档案时从 14 个区域随机选一个，实现批间自动轮换。

配置方式：`USPS_CLAW_PROXY_USER_BASE` 支持逗号分隔多区域，如 `region-us,region-us_texas,region-us_ohio,...`。代码随机选择一个，实现批间换 IP 池。

ClawBrowser 档案会根据所选出口 IP 的地理位置自动匹配指纹（时区/语言/地理位置），确保指纹与 IP 一致。

任务状态沿用模块 07：`pending`、`claimed`、`running`、`waiting_for_session`、`retry_scheduled`、`succeeded`、`dead_letter` 等。停止条件命中时，用现有 `dead_letter + provider_health.circuit_open + fetch_attempt_log/审计记录` 表达终态失败与熔断，不擅自增加数据库状态；若后续确需新增 `waiting_for_manual`，必须先在 05、07 和迁移方案中同步新增，并校验迁移器版本，不修改已入库迁移。

### 3.2 单号与批次粒度

- 客户单次提交最多 1,000,000 个候选，是**受理总量上限**，不是并发数。并发始终是"同时活跃的浏览器环境数"（由 3.3、07 的 `auto_max_environments()` 按服务器可用内存推算，`USPS_MAX_ENVIRONMENTS` 显式设置时优先）。100 万条是排队逐批处理的总量，不存在"100 万并发"。
- 客户提交的单号先按并发环境数均衡分批：并发环境数由 3.3、07 的 `auto_max_environments()` 按服务器可用内存推算（`USPS_MAX_ENVIRONMENTS` 显式设置时优先），每个环境领取一份切片。100 万条是排队逐批处理的总量，不存在"100 万并发"。
- 明细批次按并发环境数驱动：环境数越多单批越小、并行度越高。每个环境领取的切片再按 35 条拆成页面请求，逐标签页查询。百万级任务最多对应 `ceil(1,000,000 / 35) ≈ 28,572` 次页面请求，按 07 的实测速率排队，不瞬时并发。

#### 汇总去重与分批（2026-11-19 定案，对应 07 调度器）

查询发出前按四步把"客户提交"变成"页面请求批次"：

```text
多客户同时提交的待查单号
  → ① 跨客户汇总 + 保序去重（consolidate）：同一时刻多个客户的相同单号只查一次
  → ② 库内近期去重（recent_checker，默认 24h 窗口）：最近已成功抓取的单号跳过本次上游请求
  → ③ 按 35 切片（chunk）：得到 N 个页面请求批次（每批 ≤35 条 = 一个标签页一次查询）
  → ④ 环境槽分配（assign_slots）：每 10 个标签页为一代（generation），代内换标签页、代间换指纹+出口
```

- **去重的两层含义**：既去重"同时提交的单号"（跨客户 consolidate），也去重"库里最近刚查的"（recent_checker，24h 窗口内已成功的不重复抓上游）。去重服务不可用时退化为不去重，不阻断主流程；被跳过的单号直接沿用库中既有事实，客户关系/投影照常建立。
- **分层的"批"不是一回事**，禁止混用：
  | 概念 | 粒度 | 用途 | 与环境的关系 |
  |---|---|---|---|
  | 受理总量 | 1,000,000 | 一次操作最多接收 | 与并发无关 |
  | 明细批次 | 按并发环境数均衡分配 | 明细补写、进度分片 | 环境数越多单批越小，不是环境数 |
  | 页面请求批次（标签页） | ≤35 条 | 一次 USPS 页面查询 | 一个标签页一次 |
  | 环境代 | 10 个标签页 | 一套指纹 + 一个轮换出口 | 代内复用、代间轮换 |
  | 并发环境数 | 按可用内存推算 `max(2,(可用内存MB-900)//550)`，无硬上限，`USPS_MAX_ENVIRONMENTS` 优先 | 同时活跃的环境 | 决定真实并发（原「≤5」为旧残留，见 11 号文档 D2） |
- **用户举例的正确拆解**：服务器并发 5 环境 × 每环境代 10 标签页，1 万条单号 → 去重后按 35 切片约 286 个页面批次 → 每 10 个标签页一代、代间换指纹出口 → 由 5 个并发环境轮流消费。用户口径的"分 5 批每批 2000 条"是按环境数先切大块，与"按 35 切片再分给环境"结果一致；实现采用后者，因为分片更利于失败隔离、断点续写和负载均衡。
- **标签页间隔**：每处理约 10 个标签页插入一次随机化人类间隔（`tab_interval_ms` 基数随机 0.6~1.4 倍），避免机械连击被判为非人类行为。该间隔是工程节流起点，不是 USPS 安全额度，需在验收区多时段标定。
- USPS 已知单次输入上限为 35 条。系统内部 Provider 批次不得超过 35 条；若真实页面批量结果无法逐项对应或错误隔离不可靠，则降级为逐单号查询，由 07 控制速率。
- 一个环境指一个 profile、一个轮换代理出口和一个活动任务。环境数由服务器可用内存自动推算，不能等于业务批次总数，也不能从 10 标签页 × 35 条样本直接推导。
- Provider 返回值必须按规范化单号逐项给出结果。批量提交成功不代表批次内每个单号成功；批次级拒绝代表整个批次停止，不得继续提交同批余量。

### 3.3 本方案设想基线

设想实现已具备以下基础，后续实现必须保持：

- `runtime.py`：`Worker` 先领取带 `lease` 的 `FetchJob`，再调用 `enabled_provider()`。
- `ProviderError.error_class` 区分错误类别；`rejected`、`quota`、`source_invalid` 直接进入停止路径（`dead_letter`）。`challenge` 与 `circuit_open` 按重试路径处理（详见第 5.8 节熔断说明与模块 07 熔断器死锁修复）。
- `quality_gates()` 在写库前检查目标匹配、页面有效、字段完整、终态保护、事件一致性、时间置信、解析证据和事务原子性。
- 成功路径在同一 A 库事务写事实、事件、证据、outbox 和任务成功状态；失败路径写 attempt 日志、任务状态和 provider_health。
- `UspsWebProvider` 当前直接抛出 `runtime_missing`，即 fail closed。真实 Linux 采集实现未完成前，不得修改此行为。
- `usps_claw.py`（ClawExecutor）：`profiles create` 指定 `--proxy-scheme socks5` + host/port/username/country；`sticky_username()` 拼 `session-<随机>-sessTime-<时长>` 实现同一批查询内保持同一出口 IP、跨批自动换 IP；用户名从多区域池随机选州（泛美+13州）实现批间换 IP 池；`_proxy_tcp_ok()` 启动浏览器前 ClawBrowser 检测代理网关（不通时几秒内失败，省掉 40 秒启动）；`_collect()` 用批间人类鼠标/滚动轮询 + 1.5~3.5 秒随机间隔；每批 finally 双根清理约 500M 会话目录（`_cleanup_session_dir` + `_sweep_stale_sessions` 30 分钟保留期）。
- `usps_dispatcher.py`（BatchDispatcher）：`consolidate()` 跨客户去重、`recent_checker` 库内近期去重、`chunk(35)` 切片、`assign_slots()` 每 10 标签页一代、`ThreadPoolExecutor(max_workers=max_environments)` 并发、`human_interval_ms()` 0.6~1.4 倍随机间隔、`max_rounds` 失败多轮回炉；`RETRYABLE`/`TERMINAL` 区分可回炉与 fail-closed 错误。
- `auto_max_environments()`：按可用内存 `max(2, (可用内存MB - 900) // 550)` 自动推算并发环境数，显式 `USPS_MAX_ENVIRONMENTS` 优先。

## 4. Provider 接口与结果契约

### 4.1 输入

| 字段 | 说明 |
|---|---|
| `normalized_number` | 经 06 清洗后的规范化单号，禁止把客户原文直接送上游 |
| `job_id` | 当前 FetchJob ID，用于审计关联，不直接暴露给客户 |
| `reason` | `initial` / `refresh` / `manual_recheck` 等查询原因 |
| `provider_config_version` | 浏览器、profile、出口、超时和批量策略配置版本 |
| `parser_version` | 预期解析器版本，便于结果可追溯 |
| `session_ref` | profile/会话脱敏标识，禁止传 Cookie 原文 |

### 4.2 输出

Provider 成功结果至少包含：

- `normalized_number`、`source=usps_web`、`simulated=false`。
- `raw_status`、`status`：页面原文状态与系统标准状态；未知状态不得强映射。
- `events[]`：`event_id`、`occurred_at`、`status`、`description_raw`、`description_zh`、`location`、`event_code`、`time_confidence`。
- `http_status`、`page_class`、`page_valid`、`confidence`。
- `parser_version`、`raw_payload_ref` 或脱敏证据引用、`fetched_at`。
- `error_class`：成功时为 `null`；失败时为第 5 节定义的类别。

批量结果必须返回 `items[]`，每项独立携带上述字段和 `item_error_class`，不允许只返回“整批成功”而没有逐项映射。

### 4.3 数据来源标记

- 真实 Provider 结果：`source=usps_web`、`simulated=false`。
- 合成结果：`source=mock`、`simulated=true`，且只能在隔离测试中出现。注意：2026-11-18 已彻底删除 `MockProvider` 类与 `provider_config` 的 mock 行，生产链路不存在任何 mock 回退路径；上述 `source=mock` 仅作为 e2e 合成注入与隔离测试的证据标记约定，不作为可选 Provider。
- 写库前检查 `simulated`；生产启用时若结果为 `simulated=true` 或来源字段缺失，直接按 `source_invalid` 拒绝。

## 5. 查询及解析失败机制

### 5.1 失败分类与处置矩阵

以下矩阵是本模块实现、告警和验收的直接依据。表中的次数是目标初始配置，必须在 Linux 验收区按多时段数据复测后固化；它们是工程重试预算，不是上游安全承诺。

| 类别 / error_class | 典型触发 | 自动重试 | 任务状态 | Provider / 会话动作 | 处置与告警 |
|---|---|---:|---|---|---|
| `provider_disabled`、`provider_unavailable`、`provider_config_unavailable` | 未启用、缺决策引用、配置读取失败、无可用真实 Provider | 否 | `dead_letter` | 不发起请求 | ERROR 告警；检查配置/评审记录 |
| `runtime_missing`、`not_accepted` | Linux 浏览器运行时缺失、真实采集未验收 | 否 | `dead_letter` | 保持 fail closed | ERROR 告警；禁止用桌面 PoC 替代 |
| `circuit_open` | 熔断已开、连续失败触发 | 冷却半开探路 | 未超限 `retry_scheduled`；超限 `dead_letter` | 停止该 Provider 新请求，冷却期后自动半开放行 | WARN；熔断自动恢复，无需人工 |
| `challenge` | 验证码、JS 挑战、空标题+大体积混淆脚本、身份校验页 | 是，换出口回炉 | `retry_scheduled` | 换州级出口自动回炉，最多 3 次 | WARN；州级轮换下每次重试=新 IP 池，实测通过率约 2/5；连续失败触发熔断后按冷却半开 |
| `rejected` | HTTP 403、Access Denied、明确拒绝 | 否 | `dead_letter` | 终态失败该批 | WARN；该批按 §5.8 终态失败，积分按 06 冲正 |
| `quota` | HTTP 429、额度耗尽、次数提示 | 否 | `dead_letter` | 终态失败该批；有 `Retry-After` 时按提示等待 | WARN；该批按 §5.8 终态失败 |
| `upstream_5xx` | 502/503/504 等临时服务端错误 | 是，最多 3 次总尝试；退避 5/15/45 秒并加抖动 | 未超限 `retry_scheduled`；超限 `dead_letter` | 保持当前已验证速率，不加压 | 连续两个观察窗口上升则 WARN |
| `network_timeout`、`browser_crash` | 页面加载超时、驱动/浏览器异常、连接中断 | 是，同上 | 同上 | 记录 profile 健康；同一 profile 不并发 | WARN；崩溃率突增则暂停该 profile |
| `proxy_gateway_unreachable` | 代理网关 TCP 连不通（准入第 1 层） | 是，换候选出口 | `retry_scheduled` | 换下一个候选出口，不启动浏览器、未发查询请求 | WARN；连续失败检查代理服务/凭据有效性 |
| `probe_bad_status`、`probe_empty_body` | USPS 首页探测返回异常状态或空 body（准入第 3 层） | 是，换候选出口 | `retry_scheduled` | 换出口重试；不进入查询页 | WARN；首页探测失败率上升则检查出口信誉 |
| `soft_throttled` | 浏览器会话内既无结果也无失败（疑似软限流） | 是，整批换出口回炉 | `retry_scheduled` | 换环境换出口下一轮重试 | WARN；连续出现按红档处置 |
| `page_type_unknown` | 非目标页、登录页、通用说明页、维护页但无法分类 | 否；仅允许在修复分类器后重排 | `dead_letter` | 暂停该 Provider 写库，防止误解析 | ERROR；分类器缺陷工单 |
| `parse_failed` | 关键字段缺失、DOM 结构变化、JSON 不可信 | 允许同一任务一次受控重取；仍失败则停止 | 重取失败后 `dead_letter` | 保持限速；不扩大并发 | ERROR；解析器版本告警 |
| `quality_gate_rejected` | 八道闸门任一失败，如单号不匹配、终态降级、时间倒置 | 否 | `dead_letter` | 保留证据，不写事实 | ERROR；质量事故处理 |
| `not_found` | 页面明确显示无此单号/无记录 | 否 | `succeeded`，`status=not_found` | 正常结束；按刷新策略再调度 | INFO；不得当作解析失败或伪造轨迹 |
| `db_or_outbox_error` | A 库写入失败、outbox 冲突、事务异常 | 由事务回滚与调度层重入处理 | 保持原租约或回到 `pending` | 不确认消息；等待租约回收 | ERROR；按 05/08 恢复流程处理 |

说明：

- `rejected`、`quota`、`source_invalid` 直接标为 `dead_letter`（账号/协议级问题，该批终态失败，积分按 06 冲正）。`challenge` 与 `circuit_open` 按可重试路径处理，进入 `retry_scheduled`，换出口自动回炉（详见第 5.8 节）。熔断器按冷却期自动半开放行探路，全程无人工干预。
- `upstream_5xx`、`network_timeout`、`browser_crash` 的重试必须有上限、退避、抖动和幂等键；不得在收到 403/429/挑战后以“网络错误”名义继续重试。
- `parse_failed` 的一次受控重取必须使用同一已验证配置，不换 profile、不换出口、不提高并发。若页面结构已变化，应停止写入并升级解析器，而不是继续猜测字段。

### 5.2 页面取得与类型校验

解析前必须先判定“这是不是可采信的结果页”。按顺序执行：

1. **响应层校验**：HTTP 状态码、Content-Type、最终页面类型、响应大小、加载超时、是否发生跳转。非 200 或不可识别响应不得进入解析成功路径。
2. **挑战/拒绝识别**：识别验证码、Access Denied、403/429、额度提示、空标题且大体积混淆脚本、维护公告等。旧资料中“DataDome 空标题 + >100KB 脚本”的特征只作为分类器样本，不用于绕过或等待挑战完成。
3. **目标页识别**：必须存在预期的查询结果容器，并且容器内规范化单号与任务目标一致。页面中出现相同数字片段但不在目标容器，不算匹配。
4. **多结果页对应**：批量页中每个结果容器必须独立绑定到对应单号；绑定失败的项按 `parse_failed` 或 `page_type_unknown` 处理，不得按页面顺序猜测。
5. **空结果识别**：只有页面明确给出“无记录/未找到”且能绑定到目标单号时，才可产出 `not_found`。页面空白、容器缺失、脚本未渲染完成都不等于 `not_found`。

### 5.3 解析流程与质量闸门

#### 5.3.1 提取顺序

1. 优先解析页面内结构化数据（如内嵌 JSON/数据属性），但必须校验其所属单号与任务一致。
2. 结构化数据不可用或不可信时，使用 DOM 定位结果容器、当前状态和事件列表。
3. 旧版“全页文本关键词扫描”只能用于页面类型分类，不得作为事实写入依据；禁止从任意文本片段推断状态。
4. 日期解析保留页面原文，输出归一化时间和 `time_confidence`：页面给出精确时分时标记 `exact`，仅有日期或时间段时标记 `low`。USPS 页面本地时区未确认前，不得伪造确定时区。
5. 状态映射只接受已登记的标准状态；未知原文状态保留在 `raw_status`，映射失败按 `parse_failed` 或 `quality_gate_rejected` 处理。
6. 事件按稳定 `event_id` 去重。历史已有事件只追加新事件，不覆盖已确认事实；状态倒退、时间倒置、同一事件冲突进入质量保护，不直接写库。

#### 5.3.2 八道闸门（写库前强制）

| 闸门 | 检查内容 | 失败处理 |
|---|---|---|
| 1 目标匹配 | 结果单号与任务 `normalized_number` 完全一致 | `quality_gate_rejected`，不写库 |
| 2 页面有效 | `page_valid=true`、`error_class=null`、`http_status=200` | 按错误类别进入第 5.1 节矩阵 |
| 3 字段完整 | 状态存在；事件存在，或状态为明确 `not_found` | `parse_failed` |
| 4 终态保护 | 低置信结果不得把已有高置信终态改成其他状态 | `quality_gate_rejected` |
| 5 事件一致 | 事件 ID 不重复；已有事件时新结果不应为空 | `quality_gate_rejected` |
| 6 时间置信 | 每条事件 `time_confidence` 只能是 `exact` 或 `low` | `quality_gate_rejected` |
| 7 解析证据 | 有 `parser_version` 和结构化 `raw_payload` 引用 | `quality_gate_rejected` |
| 8 事务原子 | 事实、事件、证据、outbox、任务状态必须同事务提交 | 回滚并进入恢复流程 |

闸门结果以 JSON 写入 `parse_evidence`，成功和失败都保留；失败证据是定位页面变化和误判的主要依据。

### 5.4 批量结果的部分失败隔离

- 批次级失败：403、429、挑战、额度、明确拒绝或整批无法确认时，整批停止，批次内所有任务进入停止/死信流程，不继续提交后续批次。
- 单项失败：`not_found` 是有效结果；`parse_failed`、字段缺失、单号绑定失败只影响对应项。同批其他项在通过质量闸门后正常写入。
- 单项重试：`network_timeout`、`upstream_5xx`、`browser_crash` 按任务独立重试，不重跑整批；重跑整批会放大请求量，禁止作为默认策略。
- 结果落库：每个单号独立形成事实与 outbox 事件，避免一个坏项阻塞整个批次投影。

### 5.5 日志、指标与告警

#### 5.5.1 结构化日志字段

每条 Provider 日志至少包含：

`timestamp`、`env`、`service`、`worker_id`、`job_ref`、`tracking_ref`、`provider_code`、`provider_config_version`、`parser_version`、`profile_ref`、`attempt`、`error_class`、`page_class`、`http_status`、`latency_ms`、`quality_gate_result`、`outbox_event_ref`。

脱敏规则：

- 不记录完整单号，使用前缀加哈希的 `tracking_ref`，例如前 4 位 + 8 位哈希。
- 不记录 Cookie、代理账号密码、认证头、完整 URL 参数、原始页面 HTML 或客户邮箱。
- 不记录客户可见文案之外的内部错误细节；内部错误只进入受控审计日志。
- 旧版日志轮转思路可借鉴：按大小/时间轮转、限制保留数量、日志分级；当前 Linux 服务改为结构化日志 + 集中采集 + 保留期，不再写客户端本地文件。

#### 5.5.2 告警级别

| 级别 | 触发 | 响应 |
|---|---|---|
| INFO | 正常成功、明确 `not_found`、受控重试成功 | 进入指标面板，不通知 |
| WARN | 普通超时/5xx 连续两个窗口上升；解析失败率或崩溃率异常；AOutbox 积压 | 降载观察；值班人员检查，不自动改上游策略 |
| ERROR | `page_type_unknown`、闸门失败、解析器版本异常、单项大范围失败 | 暂停写库或暂停该 Provider；排查证据 |
| CRITICAL | 403、429、挑战、额度、明确拒绝、熔断、紧急停止、凭据泄露迹象 | 暂停 Provider 新请求；按第 5.8 节自动换 IP → 换环境 → 回炉重查；熔断按冷却半开自动恢复 |

阈值先在验收区标定，初始参考：普通失败率超过 5% 且持续两个 15 分钟窗口进入 WARN；解析失败率超过 10% 进入 ERROR；任何红档信号立即 CRITICAL。这些是观测起点，不是上游安全线。

### 5.6 证据留存

- 保存内容：页面类型、HTTP 状态、脱敏 DOM 片段或字段映射、解析器版本、闸门结果、错误类别、关联 job/tracking 哈希、发生时间。
- 禁止保存：Cookie、LocalStorage 原文、代理凭据、完整单号、完整页面快照、客户个人信息。
- 存储：A 库证据表保存引用，实际文件在加密存储中；仅采集域和授权管理员可按审计流程访问。
- 保留期：默认 30 天；质量事故样本经审批可延长到 90 天；到期自动清理并记录清理审计。
- 导出：必须二次确认，导出文件带水印和访问记录；不得把真实证据复制到开发/CI/Windows 备份。

### 5.7 数据一致性与恢复

#### 5.7.1 正常写入

成功路径必须在同一 A 库事务内完成：

1. 更新 `Tracking` 状态、版本、成功时间、下次刷新时间。
2. 幂等插入 `TrackingEvent`。
3. 插入 `parse_evidence`。
4. 插入 `sync_outbox`，带 `event_id`、`aggregate_version`、`payload_digest`。
5. 更新 `FetchJob` 为 `succeeded`。
6. 重置 `provider_health` 连续失败计数。

任何一步失败都回滚整笔事务，Queue 消息不确认，靠租约过期重新领取。

#### 5.7.2 失败写入

失败路径同样在事务内写 `fetch_attempt_log`、任务状态和 `provider_health`，但不写任何 Tracking/事件事实。这样可保证“失败不会污染客户轨迹”。

#### 5.7.3 跨库与队列恢复

- `sync-agent` 按 `event_id + aggregate_version` 幂等投影；B 库重复消费不产生重复轨迹。
- Redis 丢失时按 A 库 `pending / claimed / lease_until / retry_at` 重建队列；不能凭 Redis 自有的残留消息恢复事实。
- Worker 被强杀后，租约过期由其他 Worker 回收；同任务重复执行通过唯一键和事件 ID 去重。
- outbox 积压时先修复投递链路，不清空队列、不手工改投影版本。
- 数据库恢复必须先停写，再恢复 A/B，校验关键表行数、内容摘要、投影版本、账务流水和任务状态；RPO 按每日备份 ≤24 小时表述，未实测 WAL/PITR 前不承诺零丢单。
- 迁移文件入库后不得修改；新增字段或状态必须先新增迁移，并同步更新 05、07 契约。

#### 5.7.4 死信与熔断自动恢复

熔断或死信恢复流程（全程自动，无人工介入）：

1. 系统记录告警、attempt 日志和脱敏证据，供事后排查。
2. 熔断按冷却期自动半开放行一次探路，成功则复位、失败继续熔断。
3. 达到 `max_attempts` 的任务标记终态失败；管理员可显式重排选中死信任务，禁止全库无条件重放。
4. 熔断复位后从当前已验证并发继续，观察两个完整窗口无红档信号后再考虑逐级提升并发。

### 5.8 阻断后的处置机制

本机制把阻断恢复拆成可执行的自动步骤，逐级升级，避免只停不处理或无限重试。

| 步骤 | 自动动作 | 记录与结果 |
|---|---|---|
| 1 换出口 IP | 命中 403/429/挑战/额度/明确拒绝时，立即弃用当前出口，轮换到新 IP，重建环境重试该批 | 写 `provider_health`、`fetch_attempt_log`、任务引用；客户任务保留，不删除 |
| 2 留证 | 保存 HTTP 状态、页面分类、时间、环境引用、出口引用、批量大小、最近请求节奏、解析器和配置版本，不保存 Cookie、代理密码、完整单号或完整 HTML | 证据用于事后排查和分类器样本更新 |
| 3 换环境重试 | 同批连续换 IP 仍失败，整批重新入队，分配到其它环境（不同指纹 + 不同出口）重查 | 失败计入 `max_attempts`（默认 3） |
| 4 回炉重查 | 多环境轮换后仍失败的单号进入回炉队列，随下一轮批次重新分片查询 | 回炉受 `max_rounds` 约束 |
| 5 冷却退避 | 遇 429 或带 `Retry-After` 的响应按提示退避；无提示时按指数退避拉长间隔 | 熔断打开时按冷却期自动半开探路 |
| 6 终态失败 | 达到 `max_attempts` 或熔断半开仍失败，标记终态失败 | 客户显示"暂不可用/稍后重试"，不返回模拟轨迹；按 06 处理积分冲正 |

代理是采集主网络，轮换出口是它的基本能力。阻断后第一顺位即自动换出口 IP，逐级升级到换环境、回炉重查，全程无人工介入。挑战（challenge）按州级池轮换自动回炉（最多 3 次，`max_attempts` 约束）。熔断打开时按冷却期（默认 10 分钟）自动半开放行一次探路，成功复位、失败继续熔断，无需人工解封。

与 3.1 节出口可用性检测的关系：本节针对的是**查询请求已发出并被上游拒绝**后的处置；3.1 节针对的是**查询前出口本身连不通/延迟过高/首页异常**的准入筛选。前者按 §5.8 自动换 IP → 换环境 → 回炉重查，后者在发查询前换候选出口。challenge 按州级池轮换自动回炉（最多 3 次，`max_attempts` 约束），属于"未取得结果时的重试"，不属于"拿到明确拒绝后换 IP 绕过"。

## 6. 防爬机制总体要求与关键策略

### 6.1 总体要求

本节“防爬”分两层，不得混淆：

- **对上游**：目标是识别明确返回的技术限制信号并约束自身访问；遇到拒绝或挑战先暂停并按第 5.8 节处理。目标是减少误触发和快速止损，不是绕过上游风控。不把授权材料变成额外开发或发布要求，也不对业务定性作判断。
- **对自有系统**：目标是防止外部人员爬取/滥用我方 API、推导采集逻辑、窃取凭据或绕过计费；由 09 的接口安全和本第 7 节的防逆向措施承担。
- **数据源与网络口径**：17TRACK 已弃用，不走备用或兜底；udealproxy 住宅代理是采集主网络，负责为每个环境提供独立轮换出口（每次启动自动分配新 IP），解决多环境共享 IP 的问题。代理须经过凭据、会话保持和并发能力验收后才能用于真实 Provider。

明确禁止的做法：复制挑战 Cookie、隐藏自动化特征以躲避检测、等待 JS 挑战自然通过、验证码后继续用同一环境硬重试、用"成功率提升"作为访问安全证明。按 profile 绑定出口、按环境代批间轮换出口、查询前的出口可用性检测（见 3.1 节）、代间人类间隔（见 3.2 节）都是正常接入与自我保护手段。阻断后的恢复按 §5.8 自动换 IP → 换环境 → 回炉重查，是主网络方案的固有能力。旧版固定 5 线程、1/3 秒间隔、20–35 条批量等参数只作为参考记录，不是当前定值或安全承诺。

### 6.2 异常访问识别

以下信号进入风险分类，不等于自动绕过：

| 信号 | 分类 | 动作 |
|---|---|---|
| HTTP 403 / Access Denied | `rejected` | 熔断该会话，按第 5.8 节换 IP → 换环境 → 回炉重查 |
| HTTP 429 / 额度提示 | `quota` | 同上；有 `Retry-After` 时按提示等待 |
| 验证码、身份校验、JS 挑战、空标题+大体积脚本 | `challenge` | 同上；不识别为成功页面 |
| 登录页、通用说明页、维护页且无法确认结果 | `page_type_unknown` | 不写事实，暂停写库并分类 |
| 连续 5xx / 超时 / 浏览器崩溃 | 普通异常 | 有限重试；连续上升则降载 |
| 同一 profile 多次任务失败 | 会话异常 | 停止该 profile，下一批换新环境 |
| 同一出口多次触发限制 | 出口风险 | 停止该出口，阻断后自动轮换到新 IP |
| 页面结果与目标单号不一致 | 数据异常 | `quality_gate_rejected`，不写事实 |

### 6.3 访问频率控制

频率控制由 07 的调度状态机执行，02 提供信号和限制：

- 并发环境数由服务器可用内存自动推算（见 3.3、07），显式配置优先；首发仍从最低值起，不预设安全 QPS。每个环境绑定一个 udealproxy Socks5 轮换出口（启动时自动分配 IP）；批量大小在批量映射验收前按 1，验收后不超过 35。
- 多标签页节奏：每个环境代最多 10 个标签页，每约 10 个标签页插入一次随机化人类间隔（`USPS_TAB_INTERVAL_EVERY` / `USPS_TAB_INTERVAL_MS`）；代间换指纹和出口。初始间隔取保守值（如 2.5 秒基数，随机 0.6~1.4 倍），观察窗口 15 分钟；这是工程起点，不是 USPS 安全额度，任何调整须在 Linux 验收区多时段实测后固化。
- 绿档：连续多个窗口真实结果正确、无红档信号，每个窗口最多增加约 10% 并发或一个环境，观察后再决定。
- 黄档：P95 明显上升、普通失败率上升、解析失败增多时，并发乘 0.7–0.8，间隔乘 1.5–2，暂停升档。
- 红档：出现 403/429/挑战/额度/拒绝/页面误判为成功时，立即停止新请求并熔断，按 §5.8 自动换 IP → 换环境 → 回炉重查。
- 禁止以“10 个标签页 × 35 条曾成功”直接设定生产并发或推导“环境越多总量线性增长”。该样本只进入验收证据，不构成持续吞吐或环境线性扩容结论。
- 请求节奏必须记录：环境数、每环境标签页数、批量大小、间隔、时段、延迟、错误分类、资源占用和出口/会话引用，形成 07 的容量报告。

### 6.4 验证与封禁策略

#### 6.4.1 上游触发的停止

上游出现验证或封禁信号时，系统按 §5.8 自动分级处理：换出口 IP → 换环境 → 回炉重查 → 冷却退避 → 终态失败。轮换出口是采集主网络的固有能力，阻断后换 IP 是第一顺位的自动恢复手段。禁止复制挑战 Cookie、隐藏自动化特征、调低自动化痕迹或让挑战页自行完成等伪装/等待式操作。

熔断与恢复自动进行：连续失败达阈值时打开熔断，冷却期后自动半开放行一次探路，成功复位、失败继续熔断，无需人工解封。冷却半开仍失败则按 `max_attempts` 终态失败。

#### 6.4.2 自有系统的防滥用

模块 02 提供采集侧信号，具体接口和错误码由 09 固化。建议初始规则如下，最终需在验收区验证并写入 API 契约：

| 场景 | 初值建议 | 处置 |
|---|---|---|
| 登录失败 | 5 次/5 分钟 | 账号临时锁定 15 分钟；连续触发进入管理员处置队列 |
| 提交请求 | 20 次/分钟/租户 | 超限返回 429；幂等键仍有效 |
| 主动检查更新 | 同单号 5 分钟内最多 1 次 | 命中冷却不创建新 FetchJob |
| 管理端配置变更 | 任意 | 二次确认 + 审计；Provider 启用必须双人复核 |
| 异常导出/证据访问 | 任意 | 二次确认 + 审计 + 限频 |

封禁分级：限流 → 只读 → 暂停租户 → 禁用账号。不得以“提高上游访问量”作为客户套餐权益；客户可查询量受系统容量和 Provider 实测约束共同限制。

### 6.5 误伤处理

- **上游误判**：如果证据显示是维护页、页面改版或分类器误判，不视为"绕过成功"。先修正分类器，再重排任务；期间保持 Provider 停止或最低速率。
- **出口/profile 被牵连**：停止受影响对象；恢复时轮换到新出口，不批量启用新出口。
- **我方误封客户**：提供管理员解封流程，必须记录复核人、原因和证据；因误封导致已扣积分但未提供结果的，按 06 的冲正/退款流程处理。
- **误伤复盘**：每次红档或封禁事件复盘，更新分类器样本和阈值；样本必须脱敏，禁止把真实客户数据写入测试集。

## 7. 核心功能防逆向保护方案

### 7.1 保护目标

防止外部客户、内部非授权人员或入侵者：

- 取得 USPS 采集实现、profile/Cookie/代理凭据和 A 库访问方式。
- 通过前端或 API 反推内部采集端点、上游域名、内部错误码、表名和部署结构。
- 绕过计费重复调用采集、批量导出轨迹或重放内部事件。
- 替换解析器、伪装 Provider 结果或把合成数据混入客户结果。

安全原则：不依赖“藏起来”作为主要防线；客户端不可信；所有权限在服务端强制；密钥不下发；日志和错误响应不泄露实现细节。

### 7.2 物理隔离的适用范围和限制

必须如实声明：**当前 A/B 分库、角色分离、独立 systemd 服务和网络监听限制属于逻辑隔离，不是物理隔离。** 同机部署共享内核、主机 root、虚拟化层和备份介质风险。

| 隔离级别 | 说明 | 适用 | 不解决 |
|---|---|---|---|
| 逻辑隔离（当前基线） | 同主机不同数据库/角色/服务账号/端口/firewall；BFF 无 A 库凭据 | 现阶段开发与验收 | 主机 root 沦陷、共享内核漏洞、运维误操作、备份泄露 |
| 实例级强隔离 | 采集、BFF、数据库分别部署在不同云服务器实例/私有网络 | 生产推荐增强项 | 同一云账号被盗、共享镜像/密钥管理缺陷 |
| 物理隔离 | 独占物理服务器或专用硬件，独立网络与管理域 | 有合同、合规或高对抗需求时采用 | 授权人员滥用、应用层漏洞、供应链和凭据泄露 |

是否采用物理隔离由威胁模型和成本决定，不在本方案中默认为已具备。若采用，必须把采集节点放在无公网入站、仅允许必要出站和数据库连接的网络域。

### 7.3 部署与访问控制

#### 7.3.1 基线部署

- Nginx 只暴露 443；BFF 仅监听回环；admin 仅受控内网/跳板机可达。
- BFF 进程只持有 B 库凭据；Worker 只持有 A 库必要权限；sync-agent 使用专用最小权限身份；客户前端不调用任何采集端点。
- 采集服务无公网入站端口；出站按白名单限制到已确认的 USPS 目标、数据库、Redis 和监控端点。
- profile、Cookie、代理会话与密钥文件按环境隔离，权限最小化；不得进入 Git、CI、前端构建产物或普通备份。
- 生产只运行 CI/受控构建生成的只读 release 目录，校验 commit 和 SHA-256；禁止在验收/生产机改源码或临时安装依赖。
- 前端产物不含 USPS 域名、代理地址、profile 名称、A 库表名、内部错误码、source map 和采集端点，由 08/09 的黑名单扫描验证。

#### 7.3.2 增强部署

- 采集域独立实例或独立主机，数据库/Redis 在私有网络，管理访问经跳板机与 MFA。
- 使用配置中心或环境注入管理秘密，定期轮换；密钥不明文落在仓库、日志或构建缓存。
- 对 release 目录做启动哈希校验、文件完整性监控和异常进程告警。
- 审计日志写入独立、只追加、受保留期管理的存储；管理员不能静默删除自身操作记录。

### 7.4 审计与异常处理

必须记录审计事件：Provider 启用/停用、紧急停止、熔断打开/解除、配置/限速变更、解析器版本切换、死信重排、证据导出/删除、密钥轮换、发布/回滚、管理员解封。

异常处理流程：

1. 发现哈希不一致、未知进程、异常出站、源码被改、凭据疑似泄露时，立即触发 Provider 紧急停止。
2. 隔离受影响实例，撤销相关凭据和会话；不得先尝试“清掉痕迹后继续跑”。
3. 保留证据：进程清单、网络连接、审计日志、release 摘要、配置版本和证据引用。
4. 从已知可信制品重建服务；必要时按 08 流程恢复数据库并做投影/账务对账。
5. 复盘后更新访问控制、镜像和扫描规则；未经审批不得恢复 Provider。

### 7.5 旧版防破解机制的取舍

旧版 EXE 使用机器码、激活码、注册表、调试器检测、MD5 校验和代码混淆等方式保护桌面程序。当前是 Linux 服务端 Web 工作台，不向客户分发采集程序，因此：

- 不引入激活码、机器码、注册表锁定或客户端调试器检测。
- 不把密钥硬编码到代码，不复用旧版示例中的私钥或盐值。
- 不把 MD5 当完整性校验；发布链路使用 SHA-256 摘要清单。
- 防破解重点转为服务端隔离、最小权限、接口鉴权、前端黑名单、不可变制品、审计和异常响应。

## 8. 其他影响实现和上线的关键细节

### 8.1 配置项与变更审批

以下配置变更必须写审计并由授权人员审批：

`provider.enabled`、`provider.emergency_stop`、`provider_config_version`、`batch_size`、`max_attempts`、`request_interval`、`max_concurrent_profiles`、`parser_version`、`evidence_retention_days`、`challenge/quota/rejected` 告警开关、限速阈值。

禁止通过热改数据库绕过审批。真实 Provider 启用必须同时具备：决策引用、Linux 运行验收、停止条件测试、解析器准确率报告、容量报告、回滚方案。

### 8.2 解析器版本与回滚

- 新解析器先在合成样本和已获准真实样本上做影子解析，对比状态、事件、时间和字段名。
- 通过后可按 Provider 配置切换版本；旧版本保留可回退，不删除参考证据。
- 解析器回滚只改变后续解析行为，不回改已确认事实；若发现历史错误，按质量事故流程追加修正，不静默覆盖。

### 8.3 时间与状态语义

- 页面日期原文必须保留；归一化时间标注 `exact`/`low`。
- 未确认时区前不得把 USPS 页面本地时间伪装成 UTC 精确时间。
- `not_found` 是有效事实，不是失败；是否计费沿用 06 的“同客户同单号 30 天窗口”规则，单次结果不理想不自动退款，争议走账务冲正流程。
- 终态保护优先：低置信新结果不得覆盖已有高置信终态。

### 8.4 容量与依赖关系

- 35 条上限只能写入“单次输入批量”，不得写成“安全 QPS”。
- 1/2/5/10 环境验证结论必须来自目标 Linux 验收区，并注明号码集合、时段、出口、配置版本和样本数。
- 环境数增加带来的系统处理能力增长，与上游允许的访问量是两条独立曲线；任何线性扩容结论都必须有实测支撑，否则不得写入生产配置。
- 浏览器版本、依赖锁、容器镜像和解析样本必须一起纳入制品摘要，避免“同一代码、不同运行时”造成解析偏差。

### 8.5 上线前检查清单

| 检查项 | 通过标准 |
|---|---|
| Provider fail closed | 默认禁用；未验收时请求返回明确不可用，不回退 mock |
| 页面校验 | 挑战、拒绝、登录页、维护页、错误页均不被解析为成功 |
| 解析准确性 | 真实样本状态/事件/时间与页面一致；未知状态不强映射 |
| 失败矩阵 | 第 5.1 节各类别都有自动化测试或故障注入证据 |
| 批量隔离 | 单项失败不影响同批成功项；批次级拒绝整批停止；按并发环境数的明细批次与 35 条页面批次能被正确区分 |
| 数据一致性 | 成功事务、失败事务、outbox 重放、Redis 重建、Worker 强杀恢复通过 |
| 日志脱敏 | 日志/证据/告警中无完整单号、Cookie、凭据、原始 HTML |
| 限速与处置 | 403/429/挑战/额度自动换 IP → 换环境 → 回炉重查；熔断按冷却半开自动恢复；黄档降载 |
| 采集后端 | ClawBrowser 为唯一执行后端；裸内核不作为兜底；fail-closed 时不用模拟数据 |
| 指纹一致性 | ClawBrowser 自动匹配指纹与出口 IP 地理位置；UA/内核/OS/WebGL 成套自洽 |
| 代理网络 | Socks5 每环境绑定独立轮换出口；查询前完成网关/连通性/首页ClawBrowser 自动检测，不合格换候选出口；阻断后按 5.8 自动换 IP → 换环境 → 回炉，不静默直连 |
| 多环境多标签页 | 环境数按服务器内存推算；每代 ≤10 标签页；每 ~10 标签页有随机化人类间隔；跨客户汇总去重 + 库内近期去重生效 |
| 防逆向 | 前端黑名单 0 命中；BFF 无 A 库凭据；采集服务无公网入站 |
| 审计 | 启用/停用、熔断解除、配置变更、重排、证据导出均有记录 |
| 发布 | 同一固定制品、SHA-256 校验、回滚路径和备份验证通过 |
| 容量 | 有目标 Linux 多时段实测报告；无未经验证的安全 QPS 承诺 |

## 11. 历史验收证据与使用限制

以下证据来自决策日志，只用于说明限制条件和验收顺序，不构成当前容量承诺，也不改变 fail closed：

- USPS 首页可达不代表查询页可用。自动化浏览器或 curl 访问查询页曾返回 403/Access Denied，必须作为拒绝信号处理。
- Windows 用户浏览器桥接曾读取两条真实页面字段，但依赖交互式桌面和用户已通过验证的会话，只属于本机解析 PoC，不是 Linux Worker 或生产 Provider。
- Linux 默认无头 Chromium 直连查询页返回 403；patchright + Xvfb + 持久会话曾取得真实页面样本，但同出口新会话频率受限。这些是验收记录，不是稳定吞吐结论。
- udealproxy 临时凭据曾返回 401/602；代理并发与热会话复用必须在有效凭据和目标 Linux 环境重测。
- 用户十环境指纹浏览器样本只证明“多环境隔离 + 代理绑定 + 浏览器自动化”的业务形态可行，不证明自研运行时具备商业工具全部指纹能力，也不构成环境数线性扩容依据。
- 任何外部数据源在定稿/启用前先做三项冒烟：① 目标 Linux 直连与浏览器两种形态可达性；② 匿名真实数据能否取得；③ 付费/会员/限额门槛。三项未通过前不把该源写入生产链路。
- 17TRACK 因匿名演示卡和 USPS 专用额度制已弃用；不因任何临时失败自动切回。
